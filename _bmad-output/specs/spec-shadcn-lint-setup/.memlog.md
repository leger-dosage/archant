- (direction) The user requested setup of https://github.com/shadcn-ui/lint; the linked upstream SETUP.md defines setup as installing and registering the plugin without enabling rules or changing existing rule policy.
- (decision) Install @shadcn/lint as a root devDependency because the root package owns .oxlintrc.json and the workspace-wide lint:code command.
- (decision) Register @shadcn/lint through .oxlintrc.json jsPlugins while preserving plugins, rules, overrides, ignores, type-aware linting, and the existing lint:code script.
- (decision) Rely on packages/web/components.json for component aliases and the Tailwind v4 theme; add no workspace-wide settings because Archant has one UI-owning app and no shared UI package.
- (capability) CAP-1 intent: contributors can load @shadcn/lint through the existing workspace lint command. success: pnpm exec oxlint --rules lists the shadcn rules and pnpm lint:code exits 0 with the existing warning policy unchanged.
- (capability) CAP-2 intent: a clean checkout receives the plugin through the normal frozen pnpm install. success: pnpm install --frozen-lockfile succeeds and @shadcn/lint resolves from the root package without installing ESLint.
- (capability) CAP-3 intent: future work has one documented place to add design-system rules. success: docs/tech-stack.md records @shadcn/lint under the root Oxlint toolchain and points rule configuration to .oxlintrc.json.
- (constraint) Keep Oxlint as the only code linter; TypeScript 7 makes the repository documented ESLint path unusable, while @shadcn/lint supports Oxlint 1.80 or newer.
- (constraint) Preserve pnpm lint:code and its --type-aware, --max-warnings 0, and --no-error-on-unmatched-pattern behavior so local and CI verification remain identical.
- (constraint) Do not enable any shadcn rule in this change; upstream SETUP.md separates plugin setup from rule-policy selection.
- (constraint) Keep package versions compatible with Node.js 24 in CI, @shadcn/lint Node.js >=20.19, and the existing Oxlint 1.83 dependency.
- (decision) Implementation order is baseline-first for this configuration change: record current lint success, install and register the plugin, prove registration, then run the complete repository verification gate.
- (assumption) Setup means the upstream SETUP.md scope, not immediate enforcement of no-restyle or other design-system rules; rule adoption is deliberately separate because it changes UI policy and may create existing findings.
