- (direction) User asked for the runnable skeleton only; business features are cherry-picked from Sure later, each scoped through BMAD
- (capability) CAP-1 intent: a developer can install and start the project locally and reach a running API. success: pnpm install then pnpm api start:dev answers GET /health with 200 and a {"data":{"status":"ok"}} body
- (capability) CAP-2 intent: the verification gate runs end to end on a clean checkout. success: pnpm lint:code, lint:format, typecheck, test and test:e2e all exit 0
- (capability) CAP-3 intent: the data schema is shared across packages and migratable. success: drizzle-kit generates a migration, pnpm db migrate:local applies it to a local SQLite file, and derived types import from @archant/db
- (capability) CAP-4 intent: the API validates its environment and fails predictably. success: a missing required variable aborts startup naming that variable; an unknown route returns 404 with an {"error":{"code":"NOT_FOUND"}} body
- (capability) CAP-5 intent: the interface calls the API through a client typed from the routes. success: renaming a route in @archant/api makes pnpm typecheck fail inside @archant/web
- (capability) CAP-6 intent: the same application code deploys to Cloudflare and to a container. success: wrangler deploy --dry-run succeeds and docker build produces an image answering /health
- (capability) CAP-7 intent: CI runs the same gate on every pull request. success: the GitHub workflow triggers on pull_request and fails when any of the five commands fails
- (constraint) No business feature in scope: no account, transaction, budget, rule or provider call
- (constraint) Application code never branches on the platform; runtime-specific code lives only in packages/api/src/entrypoints/
- (constraint) One SQLite dialect everywhere: the driver changes per target, the schema and migrations never fork
- (constraint) No barrel files, direct imports only; the sole index.ts allowed is a runtime entrypoint
- (constraint) Tests are co-located and named *.spec.ts(x); no test reaches the network
- (constraint) Warnings fail the lint gate (oxlint --max-warnings 0)
- (decision) Local database is a plain SQLite file through @libsql/client, so a fresh clone needs no external account
- (decision) Cloudflare target is a single Worker serving both the built assets and the API, per docs/deployment.md
- (decision) AGENTS.md and docs/tech-stack.md are adopted companions: downstream reads them, bmad-spec never edits them
- (assumption) Better Auth is in the stack but is not wired in this scope; wiring it belongs to a later story
- (assumption) No CSS framework or design system is chosen here; the interface ships unstyled
- (question) Should web and api stay a single Worker from the start, or two Workers until asset serving is needed?
- (question) Does a @archant/core package for domain logic get created now, or only when the first feature needs it?
