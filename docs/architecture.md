# Architecture Spine — Archant

## Design Paradigm

Modular monolith, ports and adapters. One Node process, three packages.

- **Domain** (`packages/api/src/domain/`): pure functions and types. Balance calculation, deduplication keys, transfer matching, cash flow classification, recurring detection, statement types. No Hono, no Drizzle, no `fetch`.
- **Services** (`packages/api/src/services/`): use cases. They open database transactions, call the domain and the connectors, and are the only code that touches the database.
- **Adapters in** (`packages/api/src/routes/`, `packages/api/src/mcp/`): Hono routes and MCP tools. They parse input with Zod, call one service function, and shape the envelope or the tool result.
- **Adapters out** (`packages/api/src/connectors/`): file parsers and bank connectors behind the connector port. Pure except for the bank connectors' HTTP calls.
- **Interface** (`packages/app/`): a single-page app that talks to the API only through the typed client.
- **Data** (`packages/data/`): Drizzle schema, derived types, and isomorphic constants and helpers such as money and account types.

There is no household entity: one running instance is one household.

### AD-1 — Layers and dependency direction [ADOPTED]

- **Binds:** all
- **Prevents:** business logic tied to Hono or to the database, which cannot be tested without a server and cannot be reused by the sync route or a script.
- **Rule:** Follow the diagram above. A route calls exactly one service function. A domain function takes data and returns data. Only services import `db`. Work that must run after a commit, such as recurring detection, is called by the service, and its failure is logged without failing the request. Scripts live in `packages/api/src/cli/` and call services; `index.ts` stays the only server entrypoint. Oxlint `no-restricted-imports` overrides enforce it: `domain/**` may not import `drizzle-orm`, `hono`, `services/**` or `connectors/**`; `connectors/**` may not import `drizzle-orm` or `services/**`.

### AD-2 — The ledger is the single writer

- **Binds:** Epics 1, 2, 4, 5, 7, 8, 10; FR3, FR6, FR7, FR17, FR19, FR22–FR26, FR31–FR33, FR50–FR52
- **Prevents:** manual entry, file import, bank sync, bulk edit and transfer matching each writing money rows their own way.
- **Rule:** Only the modules of `services/ledger/` write to `entries`, `transactions`, `trades`, `entry_keys`, `balances`, `holdings`, `cost_basis_locks`, `transfers`, `rejected_transfers`, `taggings` and `transaction_attachments`, and only they delete an account; every ledger delete removes a transaction's taggings and attachments before the row. `transaction_attachments` is the ledger's because an upload checks the count and the transaction's existence in the immediate transaction that inserts, which reads `transactions`, and every ledger delete removes them first; `services/attachments.ts` keeps reading the type and cleaning the name. Other services call ledger functions. Every ledger function takes an `origin` (`user`, `rule`, `provider`, `sync`, `maintenance`) and runs in one database transaction opened with `behavior: "immediate"`, which recomputes the affected balances before committing. Foreign keys that point at `entries` or `transactions` are `ON DELETE RESTRICT`, so a bypass fails instead of cascading; the recurring payments, price changes and rejections of AD-24, which carry no money of their own, are the exception it names. An oxlint override allows importing those tables only from `services/ledger/**`, `domain/**` types, and the test code that seeds rows directly (`testing/ledger.ts`, `services/history-volume.spec.ts`). The reset of all financial data is a ledger function too, `resetFinancialData` in `services/ledger/reset.ts`: in one immediate transaction it deletes what Sure's `Family::FinancialDataReset#delete_financial_data!` deletes, every account and what it holds, imports, categories, tags, merchants, rules and their runs, budgets, recurring series and bank connections, and keeps users, sessions, assistants, invitations, `settings`, goals and the securities with their prices; a sync holding its lease refuses it with `SYNC_IN_PROGRESS` before anything goes. « Réinitialiser et précharger » runs it as a savepoint of `resetWithSampleData`'s immediate transaction in `services/sample-data.ts`, which then writes Sure's demo through `writeArchive`, the archive import's ledger calls, so a failed load leaves the household as it was. The reset's spec fails when a table of a migrated database is neither reset nor kept, so a story that adds a table says which.

### AD-3 — Connector port

- **Binds:** Epics 2, 10; FR12–FR19, FR48–FR56
- **Prevents:** a new bank or a new file format needing changes in the ledger, and file and bank imports diverging in shape.
- **Rule:** Every source produces a `ParsedStatement`, defined in `domain/statement.ts`:

  ```ts
  type NormalizedTransaction = {
  	externalId: string | null; // OFX FITID, Enable Banking entry_reference; never Enable Banking transaction_id
  	date: string; // YYYY-MM-DD, literal date part from the source (see Conventions)
  	amount: MinorUnits; // booked on the account, in the account currency, signed per AD-5
  	currency: string;
  	originalAmount: Money | null; // foreign amount of a card payment abroad, stored, never summed
  	label: string;
  	reference: string | null; // cheque or QIF N number
  	notes: string | null;
  	pending: boolean;
  	merchant?: string | null; // the merchant a bank line names, found or created by name at ingest
  	keyLabel?: string; // a bank line's label as read before Sure's clean-ups, hashed by the fingerprint (AD-7)
  };
  type ParsedStatement = {
  	transactions: NormalizedTransaction[];
  	balance: { amount: MinorUnits; currency: string; date: string } | null; // signed as the bank shows it, AD-5
  	rejected: { ref: string; reason: RejectionCode }[]; // ref is a line number or a provider id
  };
  ```

  A file parser implements `FileSource { id; detect(bytes, fileName); parse(bytes, options): ParsedStatement }`, where `options` carries the target account's currency and the CSV mapping when relevant. A bank connector implements `BankConnector { id; describeApplication; listInstitutions; startAuthorization; completeAuthorization; revokeAuthorization; listAccounts; fetchStatement(accountRef, since, today, knownMerchants); consentExpiresAt }`, where `knownMerchants` are the household's merchant names, read by the sync service before each account's statement, as Sure's `known_merchant_names`. `listAccounts` returns a stable account identity that survives a consent renewal (Enable Banking `identification_hash`). Both kinds are registered in one static list, `connectors/registry.ts`, with no dynamic loading. A connector parses its raw input or provider response with Zod, and never touches the database.

### AD-4 — Ingestion pipeline

- **Binds:** Epics 1, 2, 5, 8, 9, 10; FR16, FR18, FR22, FR31, FR37, FR40, FR50
- **Prevents:** rules seeing transfers before matching in one path and after in another, balances computed before rules exclude a transaction, and preview and confirm writing different sets.
- **Rule:** `ingest(accountId, statement, { importId | connectionId | manual, dryRun })`, in `services/ledger/ingest.ts`, runs per account, in one transaction, in this order:
  1. Reject lines dated more than 366 days after today with `DATE_TOO_LATE`, or in another currency than the account's with `CURRENCY_MISMATCH`. A line before the opening anchor goes in, as in Sure. A QIF import whose earliest line precedes the anchor moves the anchor to the day before that line, its amount kept, as Sure's `adjust_opening_anchor_if_needed!`; no other source moves it.
  2. Key matching, with key lookups batched per statement (AD-7).
  3. Pending reconciliation (AD-17).
  4. Insert new entries, attach keys to matched ones.
  5. Rules (Epic 8; a no-op until then).
  6. Transfer matching (Epic 5; a no-op until then).
  7. Statement balance (AD-8).
  8. Balance recompute.

  With `dryRun`, it returns the preview grouped as to create, already present, matched to an existing entry, possible duplicates and rejected, then rolls back. An account's own « Importer » shows that grouped preview: a file preview stores the bytes and options in `imports` with status `previewed` and returns its id. Confirming takes that id, re-runs `ingest` without `dryRun`, and answers `409 IMPORT_PREVIEW_STALE` when the groups differ from the preview. Previewed imports older than 24 hours are purged at start. « Importer les opérations », Sure's CSV `TransactionImport`, reads the file in the request it publishes in: in one transaction it inserts one `imports` row per account and runs `ingest` with `stateless`, which skips the stored-preview check, and `updateMatched`, which gives a line found present or matched the file's category, tags and notes unless the user locked the field (AD-10); its lines carry the category and tags « Mapper » chose. The CSV imports of « Réglages › Importations » show no grouped preview: Sure's « Nettoyer » table, each row's refusals on its cells, the user's cell edits sent with every request and read before the file's cells, then « Confirmer » with Sure's `dry_run` counts. Manual creation goes through the same function with a one-line statement and no key. « Importer depuis Quicken (QIF) », Sure's `QifImport`, publishes the same way, under imports of `source` `qif`; a split record's line carries `splitLines`, which `ingest` writes as the children of the line it creates, the parent excluded and locked so (AD-20), a possible duplicate left whole, and no rule runs on the parent.

### AD-5 — Sign convention

- **Binds:** all money paths; NFR1
- **Prevents:** half the code treating a purchase as positive, as Sure does, and the other half as negative; and a card balance of `-500` raising net worth.
- **Rule:** An entry amount is signed from the account's point of view: negative means money leaves the account, for assets and liabilities alike, which is how banks print statements. Stored balances are the value of an asset and the amount owed on a liability, so an asset's day balance is `previous + sum(amounts)` and a liability's is `previous - sum(amounts)`. Net worth is `sum(assets) - sum(liabilities)`. A statement balance arrives signed as the bank shows it; one ledger function, `toStoredBalance(account, signedBalance)`, converts it. No connector negates a balance.

### AD-6 — Money, currency and account types

- **Binds:** all; FR1, FR2, FR9–FR11, NFR1, NFR2
- **Prevents:** floats, two parsers of `1 234,56` disagreeing, the API and a browser disagreeing on a currency's decimals, and two lists of account types.
- **Rule:** Money is `{ amount: MinorUnits; currency: string }`, where `MinorUnits` is a branded integer. `packages/data/money.ts` owns it, with `parseAmount(text, locale)`, `formatMoney(money, locale)` built on `Intl.NumberFormat`, and a static ISO 4217 minor-unit table. An entry's currency always equals its account's; the ledger refuses anything else. Totals use `settings.reporting_currency` (default `EUR`), read through one helper, and skip, and report, accounts in any other currency. `packages/data/account-types.ts` exports `ACCOUNT_TYPES`: each type with its classification (`asset` or `liability`), its balance type and allowed subtypes, a crypto account right after an investment one, as Sure's `Accountable::TYPES`. Type-specific attributes such as a loan's terms or a crypto account's tax treatment live in `accounts.details`, a JSON column validated by a Zod schema per type; a loan's rates are integers in millionths (AD-25), and a crypto account always stores its `taxTreatment`, one of Sure's `Crypto.tax_treatments`, `taxable` unless chosen. Two predicates of the same file decide where securities go: `holdsSecurities(type)`, balance type `investment`, Sure's `Investment || Crypto`, and `supportsTrades(account)`, Sure's `supports_trades?`, any investment account and a crypto `exchange`.

### AD-7 — Deduplication keys

- **Binds:** Epics 2, 10; FR17, FR18, FR23, FR51, FR52
- **Prevents:** a key recomputed after an edit, a re-export with new `FITID`s duplicating a file, file and bank sync producing two rows for one operation, and a revert deleting what another source confirmed.
- **Rule:** Keys live in `entry_keys (entry_id, account_id, source, key, import_id, connection_id)`, unique on `(account_id, source, key)`. Manual entries have no key, but for the one an assistant's `create_transaction` gives a line with its own id, as Sure's `external_id`: `ext:<source>:<externalId>` under the source `assistant`, which no import or sync reads, so that a retry finds the line instead of recording it twice. Every other source writes `fp:<sha256 of date|amount|normalised label|occurrence index within the statement>`, plus `ext:<externalId>` when present. A bank line's fingerprint hashes its `keyLabel`, the label as Archant read it before Sure's clean-ups (counterparty, bank code, first remittance line, direction), so a label that now changes with the household's merchants never changes the key of a line already synced. Keys are written at ingest and never recomputed. An exact match on either key means "already present". Remaining lines are matched as one assignment per statement: sort lines and candidates by amount then date, and pair each line with the candidate of the same amount at the nearest date within 3 days. Candidates are entries of the account, committed before this ingest, carrying no key from this source. A line with no candidate is created; a line with a tie is created and flagged `possible_duplicate`. Reverting an import deletes the keys it wrote, then deletes an entry only if no key from another source remains, and never deletes a valuation it did not create. When the user deletes an entry, one by one or in bulk, every key it holds goes with it and nothing records the deletion, as in Sure, whose importer finds or creates by `external_id`: the next sync whose window still covers the line, or the next import of a file holding it, brings it back as a new line, paired like any other with an entry of the same amount nearby. Deleting is not hiding; excluding a transaction keeps it out of reports and keeps its keys. Label normalisation lives in `domain/normalize-label.ts` and serves fingerprints, merchants and recurring detection.

### AD-8 — Entries, valuations and balances

- **Binds:** Epics 1, 2, 6, 7, 10; FR1, FR6–FR11, FR19, FR34, FR54, FR56
- **Prevents:** two ways of storing an opening balance, history jumping when a bank is linked, and two readers inventing "current balance" differently.
- **Rule:** As in Sure's delegated types, `entries` holds every dated amount with `kind` `transaction` or `valuation`; transaction-only columns sit in `transactions`, keyed by `entry_id`, and a valuation's notes in `entries.notes`, beside its `valuation_kind`, as Sure keeps them on `Entry`. A valuation has a `valuation_kind` among `opening_anchor`, `reconciliation` and `current_anchor`, and its amount is the stored balance of AD-5, never a delta. An account gets exactly one `opening_anchor`, created with it and never deleted. As Sure's `Account::OpeningBalanceManager`, the owner or an assistant moves it in place, date and amount, keeping its id and kind; balances, and an investment or a crypto account's holdings, are computed again. The « Solde d'ouverture » sheet checks the date as Sure's valuation drawer: any day up to today, before or after the oldest entry, but never a day another valuation holds, a snapshot or the bank's `current_anchor`, as Sure's valuations are unique by date; a date it does not move, the current opening date, it checks not at all. `set_opening_balance` checks it as Sure's `OpeningBalanceManager#date_error`: a given date must precede the account's oldest other entry, pending lines and valuations included, and may fall after today; an omitted date keeps the opening date and checks nothing. Beyond Sure, neither it nor `record_valuation` dates more than a year ahead, `MAX_DAYS_AHEAD` as for statement lines: every day up to the latest entry gets a balance row, written under the write lock. A linked account's moves the same way; only an assistant's `set_opening_balance` refuses it, with Sure's `linked_account`. A revert never moves the anchor's date, as Sure's; only an import confirmed before Story 27.21, which shifted the anchor's amount and recorded `imports.previous_opening_date`, gives the lines it deletes dated on or before that date back to the amount. Every entry may precede the opening date, as in Sure: balances start at the account's oldest entry that is not pending, the opening anchor or an older one, Sure's `Balance::BaseCalculator#calculation_start_date`, and every history, the dashboard's, a goal's and the balance chart's, starts there too, as Sure's `history_start_date`; entries typed by hand are refused before 1900. The forms date a snapshot up to today; `record_valuation` may date it after, as Sure's `ReconciliationManager`, and the balances run to it; « Modifier le solde » still edits such a snapshot's amount and notes, its date unmoved. A snapshot dated on the opening date sets the anchor's amount, as Sure's `ReconciliationManager` updates the valuation already on its day; one dated before it is a `reconciliation` like any other, and a `reconciliation` moved onto the opening date is refused as taken. A file statement balance dated on the opening date leaves the anchor's amount, the owner's, as a snapshot the user entered. An account with `bank_account_id` set, which reaches its connection through `bank_accounts.bank_connection_id`, is computed backward from its `current_anchor`, down to the oldest entry, as Sure's `Balance::ReverseCalculator`: the opening date ends at the opening anchor's amount, even on or after the anchor's day, as Sure's `use_opening_anchor_for_date?`; going backward, the day before it ends there too, the opening day's movements undone for nothing, and the day after keeps the balance derived from the bank's, the gap between the two days being the cash adjustment Sure's `opening_boundary_adjustment` records, which `balances` holds in no column of its own; any other account forward, from zero on the day before the oldest entry, as Sure's `opening_starting_balances`, each valuation, the opening anchor included, setting the end of its own day. Each type carries Sure's `Account#balance_type` in `ACCOUNT_TYPES`: a property, a vehicle, an other asset and an other liability are `non_cash`, so `transactionsMoveBalance` is false for them and no transaction or trade moves their value, which each day is the valuation dated that day or else the day before's, in the forward pass and in a snapshot's `computed` and `gap` alike; a loan is `non_cash` too but its payments still move its debt, Sure's `accountable_type == "Loan"` branch. A `reconciliation` sets the end-of-day balance on its date in both directions, as in Sure's `Balance::ForwardCalculator` and `Balance::ReverseCalculator`. A file statement balance becomes a `reconciliation` carrying `import_id`, unless the user entered one on that date, in which case the user's value stays and the preview shows the gap. A link and every bank sync date the bank's balance today, whatever day it describes, as Sure's `set_current_balance`. A sync writes it as the `current_anchor` the way Sure's `Account::CurrentBalanceManager#set_current_balance_for_linked_account` does: the anchor it supersedes, dated an earlier day, becomes a `reconciliation` on that day keeping its id, so the bank figures form a chain and a line the bank never sent moves only the days between the two figures around it; an anchor dated the same day takes the new amount in place; an anchor dated after the balance's day stays where it stands, and the balance becomes the valuation of its own day, as Sure's `record_historical_balance`: the one already on that day takes the amount, keeping its id and losing its import, the opening anchor on the opening date included, else a new `reconciliation`. The superseded anchor is deleted instead when a `reconciliation` already holds its day, the user's or the file's value winning, or when it is dated on the opening date, which the opening anchor holds. Linking and relinking replace the `current_anchor` without keeping the old one. On disconnect, and on unlinking one account, Sure's `AccountsController#unlink`, the ledger's `unlinkBankAccount` clears `bank_account_id` and writes no reconciliation: the opening anchor and every `reconciliation` stay, and the bank's last `current_anchor` keeps its row as a `reconciliation` on its day, as a superseded anchor does, unless a `reconciliation` or the opening anchor already holds that day, where it is deleted; Sure leaves it a `current_anchor`, which its forward pass and its activity feed read like any valuation, and Archant's forward pass, « Soldes » tab and snapshot writes read a manual account's valuations as reconciliations. The stored history is not kept: the account is then computed forward from its history start, as Sure's `Account::Syncer` picks `:forward` once an account is not `linked?`, so a past day the backward pass derived differently takes its forward value; an unlink keeps the bank account with its connection, which goes on syncing the others and offers it for linking again, and both take the connection's sync lease first, so no running sync writes the bank's figures back. `balances` holds one row per day up to `max(today, latest entry date)`, its `cash` beside its `balance`: the balance less an investment or a crypto account's holdings (AD-22), the balance itself on any other account and on one computed backward. Every reader calls `balanceOn(accountId, date)`, which returns the last row on or before the date. Pending transactions count in no balance, as Sure's `Entry.excluding_pending`: a bank balance is a booked one, and a pending line moves balances only once booked.

### AD-9 — Cash flow classification is defined once

- **Binds:** Epics 5, 6, 7, 9; FR21, FR25, FR33, FR35
- **Prevents:** the dashboard, the budget, the assistant's income statement and the « Sans catégorie » drill-down disagreeing on which rows count, a loan payment cancelling itself out, and the « Sens » filter or a rule's type condition drifting from Sure's, which call a loan payment's or contribution's outflow a transfer while reports count it as an expense.
- **Rule:** `domain/cash-flow.ts` exports `countsInCashFlow(tx)`, which decides what every cash-flow report counts, and `direction(tx)`, which the transaction list's « Sens » filter and the rules' type condition read. A transaction counts, as Sure's `IncomeStatement`, when it is neither excluded, one-time nor pending, carries none of the internal-movement activity labels and is no transfer side, except the outflow of a `loan_payment` or `investment_contribution`, which counts as an expense whatever its sign, as Sure's `classification_sql`. Any other counted row is income above zero and an expense otherwise. Only the accounts of Sure's `IncomeStatement#eligible_accounts` count: active, included in reports, in the reporting currency (AD-6), and not tax-advantaged, `isTaxAdvantaged` in `@archant/data/account-types.ts` leaving out a PEA, an assurance-vie and the retirement subtypes Sure counts as `tax_deferred`, `TAX_ADVANTAGED_SUBTYPES`, and a crypto account whose `taxTreatment` is `tax_deferred` or `tax_exempt`, as Sure's `tax_advantaged_account_ids`; `cashFlowAccounts` in `services/reports.ts` gives them, beside `reportedAccounts`, which net worth keeps. No trade counts, a dividend or interest included, as Sure's `trades_subquery_sql`. `direction` follows Sure's `Transaction::Search#apply_type_filter` and `Rule::ConditionFilter::TransactionType`: every transfer side is `transfer`, a loan payment's outflow included, any other row income above zero and an expense otherwise; its SQL twin is `joinedTransferSide` in `services/ledger/filter.ts`, tied by a parity test. Recurring detection, matching and bills read `direction` too, as Sure's identifier and matcher leave every transfer kind out: no transfer side is a candidate of an ordinary series, and a loan payment is followed as a recurring transfer (AD-24). The counted rows are summed per category and per sign in `cashFlowByCategory`, `cashFlowByMonth` and `cashFlowByDay` of `services/ledger/queries.ts`, then read through two views. The gross view, `grossCashFlow`, is Sure's `IncomeStatement::Totals`: each side by top-level category, a sub-category's rows rolled into its parent, so a category may sit on both sides and a refund is income in its category; « Sans catégorie » on each side; each side's sub-category lines, as Sure's `subcategory_totals`. The net view, `netCashFlow`, is Sure's `net_category_totals`, derived from the gross one: each top-level category's income plus its expense, « Sans catégorie » included, an income line when positive, an expense line when negative, dropped at zero. The dashboard reads the net view; the assistant's income statement, its periods and its monthly statistics read the gross view; a budget takes its spending from the net view and its income from the gross view, as Sure's `Budget#actual_spending` and `actual_income`, and nets each category and « Sans catégorie » for its envelopes, as Sure's `budget_category_actual_spending`. A category's kind is shown, never read by either view. The list's totals leave a tax-advantaged account's rows out of income and expenses, as Sure's `Transaction::Search#totals`. The dashboard's « Sans catégorie » line opens the uncategorised list without a direction, since its net holds both signs. `transactions.one_time` is Sure's `one_time` kind, among its `BUDGET_EXCLUDED_KINDS`: set only by `PATCH /api/transactions/:id` with `oneTime`, never by a sync, an import or a rule, and cleared on both sides when the matcher proposes a transfer, the owner pairs, unmatches or rejects one, or an amount edit undoes one, as Sure's `Family::AutoTransferMatchable` and `Transfer::Creator` overwrite the kind and `Transfer#destroy!` resets it to `standard`; a deletion leaves the other side as it is; a one-time row leaves every cash-flow report and stays in balances, the list and its totals, recurring detection and the transfer matcher. `transactions.investment_activity_label` is Sure's `investment_activity_label`, one of `ACTIVITY_LABELS` in `@archant/data/activity-labels.ts` or null, set by `PATCH /api/transactions/:id` with `investmentActivityLabel` and locked as any user field (AD-10); a row labelled with one of `INTERNAL_MOVEMENT_LABELS`, `Transfer`, `Sweep In`, `Sweep Out` and `Exchange`, money moving inside an investment account, leaves every cash-flow report, budget and daily total, as Sure's `investment_activity_label_sql`, and the monthly statistics too, which read the same counted rows where Sure's `FamilyStats` and `CategoryStats` keep it, and stays in balances, the list and its totals; any other label changes nothing. The monthly statistics are Sure's `IncomeStatement::FamilyStats` and `CategoryStats`, computed once by `familyStats` and `categoryStats` in `domain/statistics.ts` from `cashFlowByMonth` over the whole history, no bound on either side, the current and future months included: each counted row on the side of its sign, summed per calendar month, and per side the median and the mean of those months' absolute sums over the months holding a line of that side; `CategoryStats` reads a row's own category only, uncategorised rows under their own key. `getCashFlowStatistics` in `services/reports.ts` gives them over `cashFlowAccounts`: the assistant's income statement reads the family's from its own unbounded day-keyed read, and gives none with `accountIds`, as Sure's `scoped_result`; the budget's suggestions read the family's expense and income medians whatever month is shown; each envelope's median and average read its category's expense side, « Sans catégorie » the uncategorised key's; a reserve in months of expenses reads the family's expense median.

### AD-10 — Manual edits win

- **Binds:** Epics 4, 8, 10; FR23, FR38, FR39, FR51
- **Prevents:** a rule, a categorisation provider or a booked version overwriting what the user set, and locking depending on who called the ledger.
- **Rule:** `transactions.locked_fields` is a JSON object, Sure's `locked_attributes`: each locked field of `LOCKABLE_FIELDS` maps to the epoch milliseconds a user write last locked it, `null` for a lock migration 0070 found without a time. Only a ledger call with `origin: "user"` adds a key or renews its time, as Sure's `lock_attr!`. Calls with any other origin never write a locked field nor change the object. The owner clears every lock of a transaction at once with `POST /api/transactions/:id/unlock`, as Sure's `unlock_for_sync!`; there is no per-field unlock, and the unlock leaves `category_origin` as it is. Category and merchant merges use `maintenance` and keep lock state. `transactions.category_origin` records who set the category (`user`, `rule`, `provider` or null), so a provider can skip categories set by rules.

### AD-11 — Transfers

- **Binds:** Epics 5, 7; FR31–FR33
- **Prevents:** a transfer stored as a flag on one side, a matcher that links without the owner's say, and results depending on the order accounts are synced.
- **Rule:** As in Sure, `transfers (id, outflow_transaction_id, inflow_transaction_id, kind, status)`, each transaction in at most one transfer, and `rejected_transfers` for refused pairs. The kind derives from the inflow account type, as Sure's `Transfer.kind_for_account`: credit card gives `credit_card_payment`, loan gives `loan_payment`, an investment or a crypto account gives `investment_contribution`, as Sure's `account.investment? || account.crypto?`, unless the outflow is also one of them, which gives `internal_move` as Sure's `Transfer::Creator` does, an other liability gives `credit_card_payment` as Sure's `account.liability?` branch, anything else, an other asset included, `internal_move`. `status` is Sure's `pending` or `confirmed`, and a pending transfer counts exactly as a confirmed one everywhere: only the list reads it, to offer the proposal. `domain/transfer-matching.ts` finds candidates: opposite amount, different account, same currency, neither side matched or excluded, both accounts active, as Sure's `transfer_match_candidates`: a split line is a candidate as any transaction, its parent never, being excluded (AD-20). A pair by hand, from the picker or an assistant, is `confirmed` at once, its sides at most 30 days apart, a rejected pair included, as Sure's `transfer_match_candidates(date_window: 30)`. Deleting a side, or editing its amount, account or currency, deletes the transfer in the same transaction; a split line is a side as any other, so unsplitting, deleting its parent, leaving it out of an edit or changing its amount in one deletes its transfer and its rejected pairs.

No tool answers earlier fields: a tool Sure lacks, such as the rule, transfer, merchant-write, label-grouping and bulk tools and Archant's `import_statement_file`, answers in the shape of its closest Sure function, writes as `create_category`'s `{ success, <row>, message }`, lists paged as `get_categories`, transaction rows as `get_transactions`'; a rule read names its rows and formats its amounts while the rule writes take ids and decimal strings, as `get_transactions` reads names and `update_transaction` takes ids. A read takes Sure's names beside ids; a write takes a name where Sure's function does, a tag's in `update_tag`, an account's exact name in the bill tools, through `accountsNamed`, and in `create_goal`, through `fundableAccountsNamed` among the accounts a goal may take, each refusing a name two accounts share rather than pick one, and otherwise ids, since a bank writes account names and a label can steer an assistant; `update_budget` and the bill tools also take a category's name, which only the owner gives. Every refusal answers Sure's JSON as the call's only text, with `isError` and no `structuredContent`, since the client checks a normal result against the tool's `outputSchema`: a tool's own refusal as Sure's `{ success: false, error, message }`, Sure's `{ error, message }` without `success` where Sure's function answers so, as `get_valuations` does through `refuseWithoutSuccess`, or `{ error, hint }` where Sure's function answers a hint, through `refuseWithHint`, an id no row has answering Sure's tool caller's `No such record` through `refuseNoSuchRecord`; a service's `AppError` the same way, its code in lower snake case and its message followed by each field as `path code` and each param as `key value`, joined by `; `; any other failure as Sure's MCP controller, `{ "error": "The tool failed to run", "tool": name }`, its name alone logged. Every tool declares MCP annotations and an `outputSchema`; a tool that writes many rows takes the count a read returned and refuses to write when the count changed. No tool deletes a category, a merchant or a tag. `delete_transaction` deletes one transaction per call, and only when the account, date and amount it names, the amount in Sure's sign, still equal the transaction's, compared inside the ledger's write; otherwise it answers `transaction_changed` and deletes nothing. It goes through the sheet's service, so a bank line comes back at the next sync still listing it (AD-7). A file reaches `/api/mcp` inside its tool call, as base64, as Sure's `upload_account_statement` takes it, at most 1 MB decoded, the route's body limit raised to 1.5 MB for it alone; it goes through `services/imports.ts`, preview then confirm (AD-4), and confirm takes the counts of the preview the owner saw. Writes keep their usual origins: a rule application `rule`, an edit `user`. A transaction, a snapshot, a goal or a transfer an assistant creates is the user's, as the owner asked for it; an import keeps the `sync` origin of every import (AD-10). `assistant_calls` records each call's client, tool, time, outcome and changed count, never arguments or results, and keeps 90 days.

### AD-20 — Splits

- **Binds:** Epic 19; FR72, FR83
- **Prevents:** a split counted twice in a balance, bank keys moving off the row the bank knows, and a child mistaken for a bank line.
- **Rule:** As in Sure, a split keeps its parent and adds children: `entries.parent_entry_id` references the parent with `ON DELETE RESTRICT`, and `services/ledger/splits.ts` writes both. The children's amounts sum to the parent's exactly. The parent keeps its deduplication keys, is excluded with `excluded` locked, and counts in no balance, list, total, report, rule or recurring detection; its children count in all of them. The parent is never a transfer candidate, being excluded; a child is one as any transaction, as Sure's, and a transfer side cannot be split. A child's label, category and merchant come from the split and its parent, as its date and amount: `updateTransaction` refuses a change of any of them on a child with `TRANSACTION_SPLIT`, as Sure's drawer disables them, and leaves its tags, notes and attachments editable; a bulk edit still gives it every field but the date, and a rule still applies to it, as rules count a split's lines. A child is never a pairing or duplicate candidate, and is never absorbed. Each user's lists group the children under their parent unless their `users.show_split_grouped` is off, Sure's `show_split_grouped?`, when both list routes return no parent and each child is a plain row; the assistant's tools always read them grouped. Deleting a parent, by any path, deletes its children first in the same transaction. Editing a split updates the children it keeps by id (AD-17). A bulk edit skips a selected parent and gives its children every field it sets but the date, which stays the parent's, as Sure's `Entry.bulk_update!`. A transaction converted into a trade (AD-22) is a parent whose only child is the trade, the trade entry's `parent_entry_id` naming it: excluded with `excluded` locked, its keys kept so a re-import finds it `present`, and dropped by every reader that drops a split parent. `splitOf`, `editSplit` and `unsplitTransaction` answer `NOT_FOUND` for it, and `splitTransaction` refuses it with `NOT_SPLITTABLE`. Deleting the trade undoes the conversion: the transaction counts again, `excluded` false and still locked. An edit of the trade that moves its date or amount is `TRANSACTION_SPLIT`. Deleting the transaction by any path, alone, in bulk or by an import revert, deletes its trade first through `deleteSplitChildren`, a later sale left short included, as any trade deletion (AD-22). Only a transaction on an account that takes trades converts, an investment account or a crypto exchange (`supportsTrades`, AD-22), `TRADES_NOT_SUPPORTED` elsewhere; a transfer side, a pending, excluded or possibly duplicated transaction, or a split's parent or child, a converted one included, is `NOT_CONVERTIBLE` (409), so a matched contribution's inflow stays a transaction counted in the cash (AD-11).

### AD-21 — Roles

- **Binds:** Epic 20; FR44, FR74–FR76
- **Prevents:** a write route forgotten by a per-route check, a permission decided by the interface, and a user created as an administrator by default.
- **Rule:** `USER_ROLES` is `admin` and `viewer`. `requireSession` puts the user on the context; `requireRole(role)` is the only check of `role` that guards a request, and answers `403 FORBIDDEN` unless the user's role equals the one named, a missing user included. `viewerReadOnly`, after `requireSession` and before the day's sync, sends every method but `GET` and `HEAD` on a guarded `/api` path through `requireRole("admin")`, so a viewer's write is refused before the route reads it; `routes/middleware/roles.spec.ts` walks every mutating route of the running app against it. No `GET` route writes. A position's cost basis lock and a typed price are a `PUT`, a `DELETE` and a `POST`, deleting a position a `DELETE` and remapping its security a `PATCH`, refused to a viewer like every other write, as is `POST /api/transactions/:id/trade`, which converts a transaction into a trade; the positions themselves are a read for every member. Reads limited to administrators, bank credentials (`/api/bank-connections/setup`), assistants, members, the export, price fetching's state (`/api/prices`) and the security search (`/api/securities`), call `requireRole("admin")`. `DELETE /api/financial-data`, the reset of all financial data, calls it too, as Sure's `ensure_admin` on its reset, though `viewerReadOnly` already refuses a viewer's `DELETE`. Better Auth's own routes sit before the middleware, so a viewer changes their name, password and two-factor there. Better Auth's `admin({ defaultRole })` is `viewer`, and every creation names its role. Only an administrator holds an MCP consent: `POST /api/auth/oauth2/consent` goes through `requireSession` and `requireRole("admin")` before Better Auth, and `grantedScopes` counts a consent only while its user is an administrator, a reader of `role` outside a request's guard, since an assistant has no session. The interface reads `role` only to hide what the server would refuse: through `isAdmin` in `lib/auth-client.ts`, which `useIsAdmin` and the guards of the settings and of a budget's forms call, and on the consent page; a request answered `FORBIDDEN`, or the window coming back, reads the session again, and a changed role runs the route guards again. Role changes and removals go through `services/members.ts`, one transaction written with Drizzle rather than through Better Auth's `setRole` and `removeUser`, which need the request's headers and write apart: the last-administrator guard, the other reader of `role` outside a request's guard, counts the administrators in the `update` or `delete` statement itself, a demotion to `viewer` deletes the member's pending invitations and OAuth consents and tokens, and a removal deletes the user, whose foreign keys cascade, and the invitations to their email. Nobody changes their own role or removes themselves there. `listAssistants` and `disconnectAssistant` read and change the signed-in administrator's consents and tokens only. Invitations store the SHA-256 of their token and expire after three days; accepting one claims it with a single conditional update, then creates the user through `auth.api.createUser` with the invitation's role, and releases the claim if that fails, since Better Auth writes on its own connection, as `/api/setup` does.

### AD-22 — Securities, trades and holdings

- **Binds:** Epic 22; FR10, FR80–FR83, NFR20
- **Prevents:** a float in a quantity or a price, an investment balance computed twice, a price provider reached without the owner's consent, and a test reaching it.
- **Rule:** Quantities and trade prices follow Sure's `db/schema.rb`: a trade's and a holding's quantity take 18 decimals and at most 16 integer digits, Sure's `decimal(34,18)`, and a trade's price 10 decimals and at most 9 integer digits, Sure's `decimal(19,10)`. They are stored as canonical decimal text, never as integers, since 18 decimals overflow SQLite's 64-bit integer past 9.22 units and 10 overflow a JavaScript safe integer past 900 719 per unit: no exponent, no `+`, no leading zero beyond one, no trailing fractional zero, `0` for zero, a leading `-` below zero. `packages/data/decimals.ts` brands them `Quantity` and `TradePrice` and gives their `parse*`, `read*`, `format*` and scaled-`BigInt` helpers; every computation on them is in `BigInt`, never `Number`, and a typed value with one decimal more is refused, never rounded. SQL reads the sign from the text, zero as `= '0'` and a negative as `like '-%'`, through `quantityNotZero`, `quantityAboveZero` and `quantityNotAboveZero` in `services/ledger/shared.ts`. Stored prices (`security_prices.price`), a holding's price and a cost basis stay integers in millionths of the currency's major unit, above Sure's four decimals, read by `micros.ts` beside `money.ts`; a day's last trade price carried into a holding rounds half to even to the millionth. A value is `quantity × price` computed in `BigInt` and rounded half to even to the currency's minor unit; the API, `get_holdings`'s source, `trades.csv` and `all.ndjson` write quantities and trade prices as their canonical text, Sure's decimal. `entries.kind` admits `trade`, whose columns live in `trades`, written by `services/ledger/trades.ts`; a buy's amount is negative (AD-5), and a trade's currency is its account's (AD-6). A trade's amount is `-(quantity × price + fee)`, the product rounded half to even, its quantity signed and positive for a buy; only an account that `supportsTrades` takes a new one or a conversion, any investment account and a crypto `exchange`, as Sure's `supports_trades?`, `TRADES_NOT_SUPPORTED` elsewhere. Everything else on trades and positions, editing or deleting a trade, the holdings recompute, positions, cost basis locks, deleting and remapping a position and `get_holdings`, takes any account that `holdsSecurities`, an investment or a crypto account, so a crypto exchange turned into a wallet keeps its trades and positions, as Sure's. A dividend or interest is a trade of quantity zero, as Sure's `Trade::CreateForm`: `trades.income_kind` is `dividend` or `interest` (`INCOME_KINDS` in `@archant/data`), null for a buy or a sale, and the checks of migration `0053` hold the quantity at zero exactly when it is set, an income's price and fee at zero, and `security_id` null only for interest on the account's cash; the ledger holds an income's amount above zero. An income needs a security the account bought on or before its date, else `not_held`, as Sure's form offers the account's holdings only; an edit changes its date and amount, never its security or its kind, and a buy or a sale never becomes one. An income only moves cash: holdings, the securities whose prices are fetched (`tradedSecurities`) and the positions' price day read only trades with a quantity, `movesQuantity` in `services/ledger/shared.ts`, as Sure's `PortfolioCache` drops a trade of quantity zero. No trade counts in a cash-flow report, an income included (AD-9), as Sure's `trades_subquery_sql`. A transaction converted into a trade (AD-20) gives it its date and amount exactly: a buy or a sale's fee is what is left, `conversionFee` in `domain/trades.ts`, refused below zero with `amount_mismatch` on `price`; a buy takes an amount at or below zero, a sale one at or above zero, an income one above zero, else `sign_mismatch` on `side`. A write may leave an account's running quantity of a security below zero, as Sure's `Holding::ForwardCalculator`: a sale above what is held on its date, or an edit, a deletion or an import revert that leaves a later sale short, commits and recomputes as any other write, with no warning, as Sure's. The ledger writes a new security in the trade's own transaction: a listing stored as the provider's symbol with its suffix, upper-cased, found again by `upper(ticker)` and its MIC; a security typed by hand without ticker or provider, found again by its ISIN. A trade's amount moves the cash, as any movement. `holdings` holds one row per account, security and day, from the security's first trade to the account's last balance day, every day after a full sale to that last day included at quantity zero, and below zero, its amount too, after a sale above what was held, derived by `domain/holdings/forward.ts`, as Sure's `Holding::ForwardCalculator`. The balance recompute of `services/ledger/balances.ts` is their only writer, and the ledger deletes them with their account. A day's price is the stored price of that day, the provider's or a typed one, else the day's last trade price, else the day before's, carried. The cost basis is Sure's `CostBasisTracker`, kept apart from the position's quantity: a buy adds `quantity × price + fee` to what the tracker holds and moves its weighted average, rounded half to even to the millionth; a sale relieves the lesser of what it sells and what the tracker holds at that average, which it leaves, and does nothing while the tracker holds nothing; the tracker emptied clears the cost basis to null, so the next buy starts over. A day's cost basis is the tracker's average whatever the quantity's sign: buy 10, sell 15 and buy 3 holds -2 at the last buy's price. An investment or a crypto account's stored balance is `cash + holdings value`, `balances.cash` holding the first term: a day without valuation moves the cash by its movements, and a valuation sets the total, the cash becoming the total less the holdings value, as Sure's `base_calculator.rb`. Holdings are computed forward only and from the recompute's own first day: the day before it is replayed from every earlier trade and each security's last stored price, the rows before it kept. A price import calls `revalueHoldings` in the transaction that writes the prices, which recomputes each account that traded the security from the later of the first day written and its first trade there, so prices and the values derived from them commit together. Prices come through `connectors/prices/`, a port apart from AD-3's, whose only adapter is Yahoo Finance; it is off until the owner turns it on, sends only identifiers, and is fetched on the first signed-in request of the day and by a button, as AD-18's daily sync. A security with no provider, or one set offline, is priced from its trades and from prices the owner types: `typePrice` in `services/prices.ts` writes a `manual`, non-provisional row in the security's currency, replacing that day's, and calls `revalueHoldings` in the same immediate transaction, as a fetch does; a security its provider prices refuses one with `PRICE_FROM_PROVIDER`. An account's positions are read by `listPositions` in `services/holdings.ts`, for the page: each security's holding on the account's last holdings day on or before today in `APP_TIMEZONE`, quantity not zero, as Sure's `qty <> 0`, by value then name, a position below zero last, and the cash of the last stored balance; `domain/holdings/positions.ts` gives each its book value, gain, gain percentage, over the book value's size as Sure's `Trend#percent`, and weight in the account's total, percentages in millionths of a percent rounded half to even, and no weight when the total is not above zero. `get_holdings` reads `listHoldings` instead, as Sure's function reads its holdings: each security's last row whose quantity is not zero on or before today, by `lastHeldHoldings` in `services/ledger/holdings.ts`, so a security sold out stays listed at its last held quantity, and its weight is Sure's, over the account's balance today. A cost basis the owner sets is a row of `cost_basis_locks` per account and security, written by `lockCostBasis` and deleted by `unlockCostBasis` in `services/ledger/holdings.ts`, only for a security the account holds above zero today, as Sure's `HoldingsController#update` checks `qty.positive?`: every reader takes it over the calculated one on a day with quantity above zero, as Sure's `cost_basis_source` ranks manual above calculated, while `holdings` keeps the calculated one, so neither write recomputes anything. A lock stands on the position held the day it was set, `locked_on`: a day at quantity zero or below on or after it, a full sale or one past it, ends that position and the lock with it, read from the partial index `holdings_not_held`, so a rebuy starts from its own buys, as Sure's tracker starts over; the row stays, read by nothing, until the owner locks or unlocks that security again. A cost basis whose book value would pass `MAX_MINOR_UNITS` is refused, as a trade's amount is. A position is deleted or remapped from its sheet, as Sure's holding drawer, by `deletePosition` and `remapPosition` in `services/ledger/holdings.ts`, for any security the account has a trade in, a short or sold-out one included, `NOT_FOUND` otherwise; each writes in one immediate transaction, selects the account's trades of the security by subquery, never by an id list held in memory, and recomputes once. `deletePosition` deletes every trade of the security on the account, buys, sales and incomes alike, as Sure's `destroy_holding_and_entries!`, its entries with them; a converted trade's transaction counts again, `excluded` false and locked, as `deleteTrade` brings it back; the position's `cost_basis_locks` row goes too, since no day at zero would end it; it recomputes from the first of those trades. `remapPosition` moves every trade of the security on the account to another, picked among the known securities and the provider's listings, never typed by hand, as Sure's `remap_security!`: `resolveSecurity` writes a new listing in the same transaction and refuses one in another currency with `currency_mismatch` on `security` (AD-6); the positions merge by themselves, since the recompute, from the earlier of the two securities' first trade on the account, derives them from the trades; a live lock moves to the new security when it has no live one, else it is dropped, as Sure's merge keeps the existing row's cost basis, and a lock a day at zero ended, on either security, is deleted first, so it never comes back on the merged history; remapping to the same security writes nothing. Neither fetches a price, nor deletes the old security or its prices.

### AD-23 — Export

- **Binds:** Epic 18; FR71
- **Prevents:** a secret leaving in an archive, a new table missing from the export, and an archive held in memory.
- **Rule:** `GET /api/export` streams a ZIP built in the request, in Sure's export format: Sure's file names and columns, and an `all.ndjson` that Sure's `SureImport` accepts, so amounts follow Sure's sign there. It sits outside the envelope and outside compression. Each table is read through `EXPORTED_COLUMNS`, an allowlist of exported columns in `services/ledger/export.ts`, the only place AD-2 lets the ledger's tables be read, beside `LEFT_OUT`, the reason for each column or table left out; a spec fails when a column of a migrated database is in neither or both. `services/export.ts` maps the rows to Sure's files, from one read snapshot (`readSnapshot` in `@archant/data/client`), a page at a time as the client takes the bytes. A story that adds a table adds it to the export or to the left-out list. Attachments leave as `attachments.json`, Sure's manifest, without their bytes, each with Active Storage's checksum computed from them at export: `content` is the one column read beyond `EXPORTED_COLUMNS`, hashed and never written. Each `Account` line carries today's balance and its `cash_balance`, both from one stored row. Trades leave in `trades.csv` and as `Trade` lines of `all.ndjson`, each naming its security by ticker, name and MIC, its ISIN and fee under `archant`; a security without a ticker writes its ISIN as one, else its name, since `SureImport::Preflight` refuses a blank ticker. Each `Trade` line carries Sure's `investment_activity_label`, `Buy`, `Sell`, `Dividend` or `Interest`, and `archant.parent_entry_id`, the transaction converted into it; `trades.income_kind` is an exported column. Interest on cash writes Sure's `Security.cash_for` ticker, `CASH-<account id>` upper-cased, and the name `Cash`, with `security_id` null, and `trades.csv` writes the same ticker with quantity and price `0`. A converted transaction leaves `all.ndjson` as an excluded `Transaction` line without `split_lines`, as Sure's own conversion leaves it, and stays out of `transactions.csv`. Holdings leave as `Holding` lines after the `Trade` lines, dated from Sure's 29 years on, naming their security as a `Trade` line does, without an `id`, a derived row having none; each `Balance` line carries its `cash_balance`. A day sold short is left out: Sure's `Holding` validates a quantity and an amount of zero or more, and the sync Sure runs after an import computes that day again from the trades. A `Holding` line on a day the account holds the security writes a locked cost basis as Sure's manual one, with `cost_basis_locked`; a day at quantity zero writes no cost basis and no source. Goals and their links leave as `Goal` and `GoalAccount` lines of `goals.ndjson`, beside `all.ndjson` and never in it: Sure's exporter writes no goal, and `SureImport::Preflight` refuses a type it does not know. Typed prices leave the same way, as `SecurityPrice` lines of `prices.ndjson` naming their security as a `Trade` line does, since the preflight refuses a price line; the provider's prices stay out, its next fetch finding them again. The archive comes back through `POST /api/sure-imports`, Sure's `SureImport`: `services/sure-import-preflight.ts` runs Sure's `SureImport::Preflight` in its order, and `services/sure-import-plan.ts` adds Archant's own refusals beside it as `invalid_import_record` and reads every line it keeps into a plan; `services/sure-import.ts` reads the file again before taking the write lock, refuses it on any error, then writes the plan in one immediate transaction, in Sure's dependency order, the categories, tags, merchants, recurring series, budgets and rules itself, and the ledger's rows through `services/ledger/sure-import.ts`, which bulk-inserts them and recomputes each new account's balances and holdings once. Nothing is stored between the two requests. Every amount is read from its decimal text into minor units, `parseDecimalAmount` in `@archant/data/money`, Sure's sign reversed for movements; `Balance` lines are checked, never stored; occurrences, payments, price changes and rejected matches are not written, the detection run after the commit rebuilding them, which leaves AD-24's writers alone over those tables. The export's CSV files come back through `POST /api/csv-imports`, Sure's `AccountImport`, `CategoryImport`, `MerchantImport`, `RuleImport` and `TradeImport`: `services/csv-import-format.ts` reads a file as Sure's `Import` does, `services/csv-import.ts` and `services/csv-import-rules.ts` read each kind and write it in one immediate transaction after the preview, run again, finds no error; accounts go through the ledger's `createAccount`, trades through `services/ledger/csv-trades.ts`, which bulk-inserts them and recomputes each account once; rules resolve their names as the archive's do, through `services/sure-rules.ts`. Nothing is stored between the requests.

### AD-24 — Recurring series, occurrences and payments

- **Binds:** Epics 9, 23; FR40, FR41, FR84–FR90
- **Prevents:** detection and matching disagreeing on what « the same day » or « the same amount » means, two date engines, a transaction paying two occurrences beyond its amount, a float in a tolerance or a score, and a payment lost when a pending line is replaced.
- **Rule:** `domain/recurring/` holds Sure's identifier, schedule engine and matcher as pure functions; `domain/recurring/schedule.ts` is the only code that computes a series' dates, and the identifier, the manual pass, the cleaner, the generator and the matcher all ask it whether a date lies within 2 days of an occurrence. Tolerances and scores are integers: an amount is within 7.5 % of a reference when `1000 × |a − r| ≤ 75 × |r|`, and a score counts ten-thousandths. A series' amount is signed as its transactions (AD-5); an occurrence's expected amount and a payment's amount are positive magnitudes in the series' currency (AD-6). `services/recurring/` writes series, occurrences and payments in one immediate transaction, run after an import, a revert or a sync commits, from « Identifier les modèles » in « Réglages › Transactions récurrentes » and « Trouver les transactions récurrentes » on `/bills`, and for occurrences on the first signed-in request of the day; a failure is logged with its code and never fails the request (AD-1). A payment and a price change reference their entry with `ON DELETE SET NULL`, and a rejection with `ON DELETE CASCADE`, as Sure's: AD-2's `RESTRICT` guards the rows that carry money, and these only point at one, so a deleted transaction leaves its payment standing and takes its rejection with it; `absorb` (AD-17) moves payments and rejections onto the survivor. A split parent is never a candidate and its children are (AD-20). No transfer side is ever a candidate of an ordinary series, as Sure's `identity_matches?`. A series with `destination_account_id` is Sure's recurring transfer: created by « Marquer comme récurrent » on a transfer (`POST /api/transfers/:id/recurring`, Sure's `create_from_transfer`), or by migration `0072` from a bill paid only by loan payments or contributions into one account, always manual, typed `transfer`, which nothing else takes, keyed by its two accounts instead of a merchant or a label, and paid by the outflows of transfers from its account into its destination, a pending transfer included (AD-11), its identity signal `transfer` scored 4000; detection's refresh and `rekey` leave it alone, the cleaner counts its outflows. « Factures » lists one only into a card or a loan, as Sure's `payable_series_ids`. The export carries every table of this decision as Sure's lines (AD-23). The Sure import (AD-23) is the one other writer of series and their recurrence rules, inserted as its archive gives them in the import's own transaction, as migration `0072` wrote some; it writes no occurrence, payment, price change or rejection, which the detection run after its commit rebuilds.

### AD-25 — Loan amortisation

- **Binds:** Epics 7, 24; FR9, FR91–FR94; NFR1
- **Prevents:** a float in a rate or a payment, a cent of difference with the lender's table, and the schedule, the overview, the chart and the projection computing one period two ways.
- **Rule:** A loan's terms live in `accounts.details` (AD-6); rates are integers in millionths, 1,82 % being `18200`. `domain/loans/` holds Sure's `AmortizationMath`, `Simulator`, `RateResolver`, `AmortizationSchedule`, `Insurance` and `PayoffProjection` as pure functions, and every loan figure reads them. They compute in exact fractions of `BigInt` and round each period's interest, payment and premium half up to the currency's minor unit, as Sure's `BigDecimal#round`; AD-22's half-to-even rounding does not apply. Payment n falls n months after origination, clamped to the month's end. A period accrues once, at the rate in force when it opened, and a payment is sized at the rate in force on its date. A schedule has at most 1 200 periods. Nothing is stored: every figure is computed on read from the terms and the account's balance.

`ofx-js` is wrapped: files over 5 MB are refused before parsing, because its SGML conversion slows down exponentially on long tag names, and a pre-pass closes empty leaf tags such as `<MEMO>`, which otherwise make it reject the whole file. Its string output is parsed by Zod, and `TRNAMT` accepts a decimal comma. The QIF parser is written in the repository: no maintained package exists. Money uses no library: amounts are integers and `Intl.NumberFormat` formats them. Date arithmetic on `YYYY-MM-DD` strings uses small helpers in `domain/`, not a date library.

Exactly one instance runs against a database. Unknown `/api/*` routes answer the `NOT_FOUND` JSON before the SPA fallback. A sync runs inside its request, except the first-visit sync of AD-18, which runs beside it in the same process; a proxy or scheduler timeout that cuts it leaves every finished account committed and the others untouched. In development, Vite serves the interface on port 5173 and proxies `/api` to the API on 8787. Turso replaces the file through `DATABASE_URL` and `DATABASE_AUTH_TOKEN` with no code change; NFR10's timings are measured on a local file.

## Deferred

- **Rules data model.** Follows Sure's, as Epic 8 describes; its tables are settled by Story 8.1. Fixed now: rules run at step 5 of AD-4, write with `origin: "rule"`, and respect AD-10. A "mark as transfer" action may only set an expectation that the step-6 matcher reads; it never creates a transfer itself.
- **Currency conversion.** No exchange rates until a non-euro account exists; AD-6 keeps the door open.
- **Roles beyond `admin` and `viewer`.** Epic 20 brings `viewer` (AD-21); per-account sharing stays out.
- **Full-text search.** `LIKE` on label and notes until NFR10's target fails: the first page of the list in under 150 ms at 100,000 transactions. SQLite FTS5 then arrives through one migration and one query helper in `services/`, the only place raw SQL is then allowed.
- **Accessibility (NFR13).** Settled in `DESIGN.md` and `EXPERIENCE.md` by `bmad-ux`.
- **Backups.** Documented in `docs/deployment.md` with `VACUUM INTO`, not run by the application.
- **Monitoring and metrics.** Pino JSON on stdout only.
- **Other deployment targets.** Configuration and documentation only, per ADR 0002.
